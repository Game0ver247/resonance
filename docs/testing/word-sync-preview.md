# Word-sync preview testing

This preview adds genuine word/syllable timing and a local diagnostic report. Stable main/Homebrew stay unchanged until the preview is accepted.

## What to try

1. Open Resonance → Lyrics → Word highlighting → Auto (default).
2. Play a song. Spotify line lyrics appear first; validated word timing can upgrade them after the provider responds.
3. Check the label beneath the lyrics: **Better Lyrics · Word sync**, **LRCLIB · Word sync**, or the existing provider with **Line sync**.
4. Try both single-line and Lyrics + artwork views, pause/resume, seek forward/back, change songs quickly, and use the existing lyric-offset controls if needed.
5. Turn Word highlighting Off to compare against ordinary line lyrics/keyword emphasis. **Retry lyrics** retries the current track while respecting provider cooldowns.

A real Spotify request for E85 / Don Toliver / OCTANE / 154 seconds returned 22 TTML lines, 21 with valid fine timing, 181 segments; its timing matched the LRCLIB line baseline. This verifies retrieval/parsing/matching, not an exhaustive listening test. Coverage varies and exact recording/version matters. The sample data was not committed.

Word/syllable timings are never generated by dividing line duration. Invalid or mismatched fine data falls back to lines. Better Lyrics is a third-party service and may require an API key for uncached queries; this preview supplies none. It uses Spicetify's configured HTTPS CORS proxy for that service (song title/artist/album/duration only, no Spotify auth). LRCLIB word data is read only when hasWordSync is true, with title/artist/album/duration checks. A conservative text/timing comparison rejects mismatched versions.

Only the active line's tokens are updated, using the existing render clock. Low power shows ordinary line text; reduced motion uses discrete word changes rather than a sweep. A bundled MIT-licensed js-yaml 4.1.1 parser handles Lyricsfile JSON-schema types; remote aliases/tags and oversized input are rejected. No extra runtime installation, audio capture or microphone permission is needed.

## Report a problem (including Linux)

1. Reproduce the problem before restarting Spotify, if possible.
2. Open **resonance → Advanced → Capture diagnostics**.
3. Share the downloaded `resonance-diagnostics-....json` voluntarily with the bug report. If Spotify blocks downloads, choose **Copy diagnostics** and paste into a text file.
4. Include OS/Spotify installation type (native or Flatpak on Linux), what you did and expected, whether the label said Word sync or Line sync, and whether playback involved AI DJ. Mention the song/version separately if you want us to test it; the report omits song IDs/titles and lyrics.

The report is local and does not upload. It includes app/Spotify version, OS/browser info, settings, current player-state availability, position/duration, lyric/analysis counts, render state and the latest 40 Resonance events. Errors are scrubbed of URLs, credentials, entity identifiers and local home paths; stack locations retain only Resonance source filenames/line numbers. It does not collect cookies, tokens, account details, lyric text, system logs, microphone audio or a CPU profile. It can show where an error was observed; it cannot guarantee the underlying cause.

## Verification scope

The full JavaScript/Python suites cover parser bounds, progress/gaps, seek behavior, late responses, cooldowns, state recovery and diagnostic redaction. Authored Chrome fixtures cover actual XML parsing, both lyric views and downloaded JSON. Live Spotify confirms a real provider response and baseline match. Interactive Linux/Windows testing remains for users; CI tests platform launchers/maintenance and shared JavaScript.
